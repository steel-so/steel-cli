# Contributing

This repo holds the Steel CLI (`packages/cli`, `@steel-so/cli`, binary
`steel`) and the TypeScript SDK (`packages/sdk`, `@steel-so/sdk`). Design
decisions live in the Steel repo: ADR 0034 (CLI and SDK), ADR 0035 (public
API v1 and personal tokens), ADR 0036 (outbound webhooks) and the wave
contract `docs/cli/README.md`.

## Setup

```bash
pnpm install            # Node 22.12+ (CI runs 22 and 24), pnpm 10
pnpm test               # Vitest, both packages
pnpm test:coverage      # with coverage thresholds (CI gate)
pnpm typecheck
pnpm check              # Biome: lint + format + organize imports (writes)
pnpm build              # tsup bundles
pnpm compile            # single-file binary for this machine (needs Bun)
pnpm --filter @steel-so/cli dev -- whoami   # run the CLI from sources
```

The CLI never touches your real config in tests: every test gets its own
`STEEL_CONFIG_DIR` and an in-memory keychain. Locally, point
`STEEL_CONFIG_DIR` at a scratch folder and use `STEEL_URL` for a local Steel
(`http://localhost:3001`).

## Layout

- `packages/sdk/openapi/openapi.v1.json` — snapshot of the Steel app's
  `public/openapi.v1.json` the SDK was generated from.
- `packages/sdk/src/generated/schema.ts` — generated by `openapi-typescript`;
  never edit by hand.
- `packages/cli/src/commands/*` — one module per command; `program.ts` wires
  them into commander; `context.tsx` resolves profile, URL and token.
- `packages/cli/src/ui/*` — Ink components and the Steel palette.
- `scripts/` — release tooling (`release.ts`, `compile.ts`) and the
  contract test (`contract.ts`, `lib/openapi-compat.ts`).

## Regenerating the SDK

```bash
pnpm --filter @steel-so/sdk generate                      # default source
pnpm --filter @steel-so/sdk generate ../steel/public/openapi.v1.json
pnpm --filter @steel-so/sdk generate https://homologacao.stratustelecom.com.br/dev/api/v1/openapi.json
```

Without an argument the source is `STEEL_OPENAPI_SOURCE`, then a sibling
Steel checkout (`../steel/public/openapi.v1.json`); with neither, the script
fails instead of guessing. Commit both the snapshot and `schema.ts`; CI runs
`generate:check` and fails when they drift.

`src/models.ts` names the types the SDK exports. Most come straight from
`components.schemas`; the rest (request bodies, the webhook endpoint page,
the create-endpoint result…) are derived from the operations, so a rename in
the document breaks the typecheck here instead of silently changing the
public API. The listen stream and the delivery body (`WebhookEvent`,
`WebhookListenReady`, `WebhookListenFrame`) are SSE, not JSON operations, so
they are written by hand after ADR 0036.

## Rules

- **Language:** code, comments, commits, PRs and logs in English; everything
  the user reads (messages, hints, help, README) in pt-BR.
- **Errors:** commands throw `CliError` (message + hint in pt-BR, stable
  `code`, exit code). The SDK never throws for HTTP/network failures.
- **Output:** `--json` (and non-TTY stdout) is a stable contract; a breaking
  change to it is a major version (ADR 0034). No colors outside a TTY,
  with `NO_COLOR`, `--no-color` or `--json`.
- **Dependencies:** exact versions only, at least two weeks old
  (`minimumReleaseAge` in `pnpm-workspace.yaml` enforces it for the whole
  tree).
- **Commits:** Conventional Commits (commitlint runs in CI on PRs). Header up
  to 100 characters, lower-case subject, no trailing period.
- **Versioning:** SemVer, independent of the app's CalVer. Both packages
  are released together with the same version, taken from the git tag.

## Releasing

A release is a `v<semver>` tag; nothing is committed. `main` only takes pull
requests, so the version in the `package.json` files is not the source of
truth: `.github/workflows/release.yml` stamps the tag's version into both
packages on the runner before building and publishing.

```bash
git switch main && git pull
pnpm release:tool next            # suggests the next tag from the commits
pnpm release:tool next minor      # or force patch / minor / major
git tag -a v0.2.0 -m v0.2.0
git push origin v0.2.0
```

Before 1.0.0 a breaking change bumps the minor and a feature the patch.
Tags with a prerelease (`v1.0.0-rc.1`) publish to npm under `next`, are
marked as prerelease on GitHub and skip Homebrew.

The workflow then:

1. **verify** — the tag is `v<semver>`; lint, typecheck, tests with
   coverage and build.
2. **contract** — the contract test against the Steel homologação
   (ADR 0034), see [Contract test](#contract-test). Nothing is published
   unless it passes.
3. **binaries** — `bun build --compile` (`scripts/compile.ts`) on a native
   runner per target (`linux-x64`, `linux-arm64`, `darwin-x64`,
   `darwin-arm64`, `windows-x64`), with a smoke test of each binary. The
   keychain addon is native, so each target is built on its own OS/CPU.
   Pull requests that touch the release tooling run this job too.
4. **github-release** — `SHA256SUMS`, signed build provenance for every
   asset (`actions/attest-build-provenance`), and the release with notes
   generated from the Conventional Commits since the previous tag (this is
   the changelog). `install.sh` is attached as well.
5. **npm** — `pnpm pack` + `npm publish --provenance` of `@steel-so/sdk`
   and then `@steel-so/cli`, authenticated by npm **trusted publishing**
   (OIDC, no token). Versions already on npm are skipped, so re-running is
   safe.
6. **homebrew** — renders `Formula/steel.rb` from `SHA256SUMS` and pushes it
   to `steel-so/homebrew-tap` over SSH. Skipped with a notice without
   `TAP_DEPLOY_KEY`.

A failed run can be re-run from the Actions tab; the release upload uses
`--clobber` and the formula push is a no-op when nothing changed.

Build metadata (`steel --version`, `steel version`) comes from
`scripts/lib/build-info.ts`: `GITHUB_SHA` (or `git rev-parse HEAD`) and the
build date (`SOURCE_DATE_EPOCH` when set), injected as `process.env.*`
defines by tsup and Bun. From sources it says `dev`.

### Contract test

Job `contract` of `release.yml`. It runs on every tag (before the GitHub
release and npm), on pull requests that touch the release tooling or the
SDK snapshot, and on demand: Actions › Release › **Run workflow** (an
optional Steel URL, homologação by default). A manual run only runs this
job; it never builds binaries or publishes.

1. **OpenAPI compatibility** — downloads
   `https://homologacao.stratustelecom.com.br/dev/api/v1/openapi.json` and
   compares it with `packages/sdk/openapi/openapi.v1.json`, the snapshot
   the SDK was generated from. A removed path, operation, success status or
   field, a type change, or a newly required request field or parameter
   fails the release; additions pass. The checker
   (`scripts/lib/openapi-compat.ts`) is a port of Steel's
   `src/openapi/v1/compat.ts` (`pnpm openapi:v1:compat` there): keep the
   two in sync. Locally: `pnpm contract:check [url-or-path]`.
2. **Read-only smoke** — with the secret `STEEL_CONTRACT_TOKEN`, builds the
   CLI and runs `steel whoami --json`, `steel sd catalog --json` and
   `steel crm pipelines --json` against
   `STEEL_URL=https://homologacao.stratustelecom.com.br`, checking that each
   prints JSON and exits 0. It fails when the token has `api:write`.
   Without the secret it is skipped with a notice.

A snapshot that is newer than the homologação (routes the Steel has not
deployed there yet) fails step 1 as well: release only after the Steel
change reaches the homologação.

### One-time setup (repository owner)

**npm.** The organization `steel-so` and both packages exist (0.1.0 was
published by hand on 2026-10-18). The account requires 2FA for writes, so a
granular token cannot publish from CI; the workflow uses trusted publishing
instead:

1. On npmjs.com, for `@steel-so/sdk` and for `@steel-so/cli`: package
   Settings › **Trusted Publisher** › GitHub Actions, organization
   `steel-so`, repository `steel-cli`, workflow filename `release.yml`
   (no environment).
2. Optionally, in the same Settings, set **Publishing access** to "Require
   two-factor authentication and disallow tokens": trusted publishing keeps
   working and no token can publish.

There is no `NPM_TOKEN` secret.

**Homebrew tap.** `steel-so/homebrew-tap` exists (users run
`brew install steel-so/tap/steel`).

1. Generate a key pair just for this: `ssh-keygen -t ed25519 -N "" -C
   steel-cli-release -f tap_deploy_key`.
2. In `steel-so/homebrew-tap` › Settings › Deploy keys, add
   `tap_deploy_key.pub` with **Allow write access**.
3. In `steel-so/steel-cli`, save the private key `tap_deploy_key` as the
   secret `TAP_DEPLOY_KEY`. Delete both local files afterwards.

The formula is written to the tap's `main` branch; keep that branch free of
rules that require pull requests for the deploy key.

**Contract token.** `STEEL_CONTRACT_TOKEN` is a personal token on the
Steel homologação, used only for the read-only smoke:

1. Sign in at `https://homologacao.stratustelecom.com.br` with a dedicated
   account that is a member of a test workspace with the **ServiceDesk**
   and **CRM** modules on (e.g. the smoke workspace) — not a personal
   account.
2. Profile menu › **Configurações › Segurança › Tokens de API** › new
   token: that workspace, modules ServiceDesk and CRM, scope **`api:read`**
   (never `api:write`), the longest expiry offered. Copy the value
   (`stl_pat_...`); it is shown only once. `steel login --profile
   homologacao` with the same choices works too (`steel whoami` shows the
   token's scopes and expiry).
3. In `steel-so/steel-cli` › Settings › Secrets and variables › Actions,
   save it as the repository secret `STEEL_CONTRACT_TOKEN`.
4. Before it expires, create a new one and replace the secret; revoke the
   old one in the same screen.

**Signing.** No secret is needed: binaries are signed through GitHub's
artifact attestations (Sigstore, keyless) and npm packages carry
provenance. macOS binaries are not notarized (no Apple Developer account);
Homebrew and `install.sh` downloads are not quarantined, but a `.tar.gz`
downloaded with a browser is: `xattr -d com.apple.quarantine steel`.
